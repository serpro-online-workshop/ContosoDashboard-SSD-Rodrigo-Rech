## Dependencies and Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: T001-T002 have no feature-code dependencies and establish the test project and runtime configuration.
- **Foundational (Phase 2)**: T003-T014 depend on Setup; T003-T007, T009-T010, and T013 can proceed in parallel after T001, while T008, T011-T012, and T014 follow their model/fixture prerequisites. This phase blocks all user stories.
- **User Story 1 (Phase 3)**: T015-T019 depend on the foundational schema, contracts, storage, scanner, and fixtures; T015-T016 are written before T017-T019.
- **User Story 2 (Phase 4)**: T020-T022 depend on the upload service shell and document data from US1 because the centralized authorization predicates are added to `DocumentService.cs`.
- **User Story 3 (Phase 5)**: T023-T028 depend on US2 authorization predicates; query and endpoint tests precede implementation.
- **User Story 4 (Phase 6)**: T029-T031 depend on US1 storage/upload behavior and US2 authorization; the lifecycle tests precede service/UI changes.
- **User Story 5 (Phase 7)**: T032-T035 depend on US2 authorization and the document workspace; sharing tests precede notification/service/UI changes.
- **User Story 6 (Phase 8)**: T036-T044 depend on the core document service and authorization behavior from US1-US5; its test tasks precede integration implementation.
- **Polish (Phase 9)**: T045-T049 depend on all desired stories and provide the final documentation, security, build, performance, and manual validation pass.

### User Story Completion Order

- **US1 (P1)**: First MVP increment after Foundational; no other story is required to validate basic upload and organization.
- **US2 (P1)**: Follows US1 because it extends the same `DocumentService.cs` with centralized resource authorization and project document UI.
- **US3 (P1)**: Follows US2 because search, list, preview, and download must reuse the completed authorization predicates.
- **US4 (P2)** and **US5 (P2)**: Can be implemented in either order after US2; they both extend the existing document service/workspace and should be merged sequentially when working in one branch.
- **US6 (P3)**: Follows the core lifecycle and sharing behavior so task, dashboard, notification, and reporting views use stable document permissions and activity records.

### Within Each User Story

- Write the story tests first and verify that they fail for the missing behavior.
- Implement models/contracts before service behavior, service behavior before endpoints/UI, and core behavior before integration.
- Keep authorization in services even when the UI hides an action.
- Run the story's independent test criteria at its checkpoint before starting dependent integration work.
